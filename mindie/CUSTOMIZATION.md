# MindIE 镜像定制指南

## 前言
### 重要声明
- 镜像定制可能会导致系统不稳定、安全风险和性能下降。
- 强烈建议在开发环境中谨慎操作，经过充分测试后再更新生产环境。

### 前提条件
- 具备 Docker/Kubernetes 基础知识
- 了解容器化技术原理
- 熟悉 Linux 基本操作
- 具备基本的 Shell 脚本编程能力
- 建议拥有网络和系统管理背景

## 可定制文件
1. Dockerfile
2. requirements.txt
3. server.js
4. 新增其他需要的文件，包括镜像构建过程中需要用的辅助文件，以及需要置入镜像内的各类脚本。

## 常见定制场景

### 1. 云上/平台部署场景
#### 核心挑战
服务配置的动态化是容器化部署中的关键难题。在当前设计中，服务配置依赖于静态文件config.json，而云原生环境要求配置能够灵活、安全地动态调整。也就是说，“一行命令启动服务”，而不必再额外进入容器修改任何文件。

#### 关键要求
- 容器启动即服务就绪
- 避免手动修改容器内文件

#### 定制步骤
1. **选择合适的配置注入方法**
    
    根据项目需求和配置的复杂性，选择合适的配置注入方式。对于配置较为简单、固定的服务，可以选择**静态配置挂载**，即通过将预先配置好的文件挂载到容器中。而对于需要在运行时动态配置的场景，可以选择**动态配置传递**，通过环境变量、命令行参数或使用专门的工具（如 Shell 脚本、Python 或 jq）进行配置调整。

    > 具体信息见后文 `配置注入方法` 一节。

2. **编写所需要的文件**
    
    根据选定的配置注入方法，编写相关的配置文件或启动脚本。若使用动态配置传递，您可能需要编写一个配置脚本，该脚本可以处理传入的参数或环境变量，并据此修改目标配置文件。对于静态配置挂载，您只需准备好配置文件并确保其权限设置正确，符合容器内部用户的要求。

3. **放入启动脚本**
   
    在 Dockerfile 中，将所编写的启动脚本或配置文件复制到容器内指定的位置。确保这些文件能够在容器启动时被正确读取，同时设置执行权限。

4. **指定 `entrypoint`**
    
    在 Dockerfile 中，您需要使用 `ENTRYPOINT` 或 `CMD` 指令，指定容器启动时执行的之前您编写好的脚本。或者在容器启动时，指定 `--entrypoint`，可以达到同样的效果。


#### 配置注入方法
1. 静态配置挂载
    - 定义：直接将预先配置好的 `config.json` 挂载到容器内，替换镜像中默认的文件。
    - 适用场景：配置相对固定与统一的服务场景。
    - 关键注意事项：
        - 确保文件权限与容器内用户一致，默认用户为mindieuser，1000:1000，文件权限应当设置为640。
        - 避免将敏感信息直接写入文件。
        - `config.json` 的默认位置为 `/home/mindieuser/Ascend/mindie/latest/mindie-service/conf/config.json`。

2. 动态配置传递
    1. 配置传递方式

        - 参数传递

            Docker/Kubernetes 命令行直接传入参数。


        - 环境变量传递

            通过 `-e` 或 `env` 注入配置。
    
    2. 配置转换工具

        - **Shell (sed/awk)**

            **优点**：轻量、无额外依赖，适合简洁的文本替换。

            **缺点**：正则替换可能存在安全风险，且不支持复杂结构的解析。

            **案例**： 使用 Shell 脚本接收传入参数并修改 `config.json` 文件：
            ```sh
            while [[ "$#" -gt 0 ]]; do
                case $1 in
                    --model) MODEL_WEIGHT_PATH="$2"; shift ;;
                    *) 
                        echo "Unknown parameter: $1"
                        echo "Please check your inputs."
                        exit 1
                        ;;
                esac
                shift
            done

            sed -i "s|\"modelWeightPath\"\s*:\s*\"[^\"]*\"|\"modelWeightPath\": \"$MODEL_WEIGHT_PATH\"|" $CONFIG_FILE
            ```
            其中 `$CONFIG_FILE` 为 `config.json` 的路径。该脚本将接收传入的 `--model` 参数并更新 `config.json` 中相应的 `modelWeightPath` 项。如果需要使用环境变量，则可以省略参数解析部分，通过直接读取环境变量来配置。


        - **Python**

            **优点**：强大的 JSON 处理能力，支持复杂结构和嵌套数据的解析。

            **缺点**：相较于 Shell 脚本，Python 需要额外的运行时环境，因此会带来一些性能开销。

            **适用场景**：需要处理复杂的 JSON 配置文件，或者当配置中包含嵌套结构时，Python 提供了更为直观的解析和处理方式。

            **案例**： 使用 Python 读取并修改 config.json 文件中的配置项：
            ```python
            import json
            import os

            config_file = 'config.json'
            with open(config_file, 'r') as f:
                config = json.load(f)

            model_weight_path = os.getenv('MODEL_WEIGHT_PATH')

            if model_weight_path:
                config['modelWeightPath'] = model_weight_path

            with open(config_file, 'w') as f:
                json.dump(config, f, indent=4)
            ```
            在该案例中，Python 通过环境变量动态传递配置项并更新 JSON 文件。

        - **jq**

            **优点**：专业的 JSON 处理工具，支持丰富的查询和修改操作，语法简洁。

            **缺点**：需要额外安装 `jq`，基础镜像中不包括。

            **案例**：使用 `jq` 修改 JSON 文件中的配置项：
            ```sh
            MODEL_WEIGHT_PATH=$(echo $MODEL_WEIGHT_PATH)
            jq --arg model_weight_path "$MODEL_WEIGHT_PATH" \
                '.modelWeightPath = $model_weight_path' $CONFIG_FILE > tmp.json && mv tmp.json $CONFIG_FILE
            ```


### 2. 开发测试场景

在容器化环境中，通常会使用不同类型的镜像来支持应用的不同生命周期阶段。除了**生产镜像**，常见的还有**开发镜像**和**测试镜像**。这三种镜像在基础配置上有很多相似之处，但也根据用途有所不同，特别是在用户权限，以及所需工具和环境的配置上。

#### 1. 更改用户

- 若想将容器内的默认运行用户切换至 `root`，可以参考[Dockerfile.Ubuntu-root](.\aarch64\Dockerfile.Ubuntu-root)。
- 若想更改用户名与其他设置，请在Dockerfile中该部分进行如下修改：
  - 调整用户创建部分
    ```docker
    # Create User and Set Working Directory
    RUN groupadd -g 1000 mindie && \
        useradd -u 1000 -g 1000 -m mindieuser

    WORKDIR /home/mindieuser
    USER mindieuser
    ```
  - 更改各环境变量中的路径，例如：`ENV ASCEND_TOOLKIT_HOME=/home/mindieuser/Ascend/ascend-toolkit/latest`，中的 `/home/mindieuser` 需要根据实际情况修改，**请务必正确设置所有环境变量**。

#### 2. 生产镜像

生产镜像是应用部署的核心镜像，本仓库提供的构建镜像示例即为生产镜像。通常包含了应用运行所需的最小依赖和环境，旨在确保高效、稳定地运行，因此它通常不会包含开发工具和调试工具，避免引入不必要的复杂性和安全风险。

#### 3. 开发镜像

开发镜像是为开发人员提供支持而定制的镜像。它基于生产镜像，通过安装额外的工具和库，为开发人员提供调试、构建和编程所需的环境。开发镜像通常会包括以下几类内容：

- **调试和构建工具**：如 `gdb`、`strace`、`vim`、`git`、`cmake` 等。
- **开发依赖**：一些常用的开发库和工具，确保开发人员能够在镜像中进行高效的编程工作。
- **非生产环境配置**：例如，开发镜像可能会关闭某些生产环境中的优化设置，以便调试和开发。

通过将这些工具和依赖添加到基础镜像中，开发镜像为开发者提供了一个完全自给自足的环境，可以在其中直接进行代码编辑、调试和构建工作。

#### 4. 测试镜像

测试镜像用于应用的自动化测试和质量验证。它与开发镜像相似，但会包含专门为测试所需的工具和框架。测试镜像通常包括：

- **单元测试框架**：如 `pytest`、`gtest` 等。
- **代码覆盖率工具**：如 `lcov`、`gcov` 等。
- **模拟和测试依赖**：如模拟工具 `mock` 或其他模拟服务。
- **日志和调试工具**：如 `curl`、`telnet` 等，用于调试测试过程中的问题。

测试镜像的目标是提供一个与生产环境相似的环境，以确保代码能够在接近真实场景的条件下进行测试，验证功能是否正常。

#### 5. 从基础镜像构建定制镜像

构建开发镜像和测试镜像的核心步骤是基于现有的生产镜像，通过修改和扩展其内容来满足特定的需求。通常，这些扩展包括安装额外的工具和依赖，并设置环境变量来控制不同的配置。

**镜像构建的关键步骤：**

1. **从生产镜像开始**：选择一个合适的生产镜像作为基础。
2. **添加工具和依赖**：根据开发/测试需求安装必需的工具。
3. **配置环境**：为开发提供适宜的默认配置，如开发用户权限、调试设置、设置环境变量等。
4. **确保与生产环境的兼容性**：尽量保持与生产环境的一致性，避免不必要的差异导致环境不一致的问题。

以下包括各种常见定制操作：
> 该文件不可直接使用，仅作为参考。
```Dockerfile
# 1. 从生产镜像开始
FROM mindie:prod

# 2. 设置维护者信息
LABEL maintainer="your-email@example.com"

# 3. 更新包列表并安装基本工具（需要切换至root用户）
USER root

RUN apt-get update && apt-get install -y \
    curl \
    git \
    vim \
    build-essential \
    gdb \
    strace \
    cmake \
    python3-pip \
    python3-dev \
    && rm -rf /var/lib/apt/lists/*

# 4. 安装特定版本的 Python 依赖
RUN pip3 install --no-cache-dir \
    pytest \
    pytest-cov \
    mock

# 5. 从源码安装软件（例如安装某个库）
RUN curl -L https://example.com/3rd-party-lib/archive/v1.0.0.tar.gz -o /tmp/3rd-party-lib.tar.gz \
    && tar -xvzf /tmp/3rd-party-lib.tar.gz -C /tmp \
    && cd /tmp/3rd-party-lib-1.0.0 \
    && make install

# 6. 设置开发环境的用户（假设需要一个非root用户）
RUN useradd -m developer && echo "developer:password" | chpasswd && adduser developer sudo
USER developer
WORKDIR /home/developer

# 7. 设置环境变量
ENV TEST_MODE="true" \
    PATH=$PATH:/usr/local/sbin:/usr/local/bin

# 8. 设置工作目录和默认命令
WORKDIR /home/developer/projects

# 9. 设置启动容器时执行的命令
CMD ["bash"]
```

### 3. 多架构/系统兼容性

在构建多架构或跨平台的 Docker 镜像时，可能会遇到多种挑战，建议尽量保持宿主机环境与目标镜像环境的一致性，如果可能，在与目标环境完全相同的宿主机上进行构建，这样可以减少由于架构差异、工具链不匹配、系统库不兼容等问题带来的麻烦。

另外，使用 Docker 的 `buildx` 等多平台支持工具可以有效简化跨平台构建过程，而合理优化 Dockerfile 和构建流程可以显著提升构建效率并降低出错率。

以下是一些常见的问题和解决方案。

#### 1. 架构相关的兼容性问题

当在不同架构之间切换（例如从 x86_64 架构到 ARM 架构）时，可能会遇到以下问题：

- **软件包不兼容**：某些软件包可能只支持特定架构，一些应用程序和库可能没有为 ARM 架构构建或优化版本。
  - **解决方案**：检查是否有针对目标架构的预编译二进制文件，或者使用源代码进行编译，确保可以在该架构上运行。
  
- **跨架构的二进制依赖**：一些二进制文件（如静态库或共享库）可能会在不同架构之间不兼容。这尤其影响到基于源码构建的镜像，可能需要特别的标志或选项。
  - **解决方案**：在 Dockerfile 中明确指定编译工具链，确保编译器使用正确的架构标志（例如 `gcc -march=armv7`）。
  
#### 2. 架构相关的底层库和系统工具问题

不同架构的系统工具和库版本可能有所不同，尤其是跨平台或不同操作系统之间（如 Linux 和 Windows）的迁移。

- **依赖问题**：一些系统依赖（如 `glibc`、`libc` 或特定于架构的工具链）可能会在不同架构下表现不一致。
  - **解决方案**：确保构建过程中使用的基础镜像适配目标架构，并且相应的系统库在目标架构中可用。对于多架构支持，可以考虑使用 `multiarch` 镜像。

- **操作系统差异**：不同操作系统（例如 Ubuntu 与 CentOS）可能在默认的系统工具和库上有所差异，导致构建失败。
  - **解决方案**：使用通用的基础镜像（例如 `debian` 或 `alpine`），避免使用与操作系统紧密绑定的工具或库，或者明确安装所需的依赖。

#### 3. 构建工具与环境的兼容性问题

不同架构和操作系统可能对构建工具（如 `make`、`cmake`、`apt`、`yum`）的支持存在差异，导致构建过程中出现问题。

- **编译器和工具链兼容性**：构建过程依赖于编译器（如 `gcc`）和工具链，这些工具在不同架构上可能会有所不同。
  - **解决方案**：确保 Dockerfile 中使用的编译器和工具链支持目标架构。必要时，使用跨平台工具（如 `clang`）进行编译，或者在构建时使用合适的工具链（例如使用 `--target` 标志）。

- **架构相关的容器引擎问题**：不同的容器引擎（如 Docker 或 Podman）可能在支持多架构方面存在差异，尤其在使用 ARM 架构时。
  - **解决方案**：确保容器引擎已启用多架构支持，并使用适当的镜像和平台标志（如 `--platform`）。

#### 4. 构建工具的多架构支持

现代的 Docker 支持通过 `buildx` 扩展多架构支持，但有时构建过程可能由于特定版本的 Docker 或构建工具不支持某些架构而失败。

- **构建工具版本差异**：不同版本的 Docker 可能支持不同的架构，导致构建失败。
  - **解决方案**：确保使用 Docker 的最新版本，并启用 `buildx` 支持，确保跨架构构建正常工作。


## 定制方法与技术

### 镜像定制指导

#### 方法论

1. **配置解耦**  
   在镜像定制中，保持配置与应用逻辑的解耦是非常重要的。通过将配置文件与镜像分离，允许在不同的环境中灵活地更改配置，而无需重新构建整个镜像。这样做不仅增强了镜像的可复用性，还提高了运维的灵活性和效率。

2. **参数化配置**  
   通过参数化配置，可以让镜像的构建过程更加灵活。使用 `ARG`、`ENV` 和其他参数化机制，使得在构建时能够传入动态的参数，避免了硬编码的配置。这使得镜像可以在不同的环境下进行构建而无需修改 Dockerfile。

3. **版本管理**  
   在镜像的定制中，合理的版本管理至关重要。通过对关键依赖（如操作系统、软件包、工具版本等）进行版本控制，可以保证每次构建的镜像都符合预期的标准，避免因版本差异导致的问题。

#### 定制途径

- **Dockerfile 扩展**  
   通过继承基础镜像并在 Dockerfile 中增加额外的依赖、工具、配置等，能够实现高度定制化的镜像构建。Dockerfile 扩展是一种简单直观的定制方法，适用于大部分应用场景。

- **自定义脚本**  
   使用自定义脚本来进行更复杂的配置和初始化任务，尤其在需要执行一些环境设置、动态配置文件修改、调试工具安装等操作时，脚本定制能够提供极大的灵活性。

- **挂载配置文件**  
   挂载外部配置文件是一种常见的定制手段，尤其适用于需要在容器启动时加载不同配置的场景。通过挂载宿主机上的配置文件，能够避免对镜像本身进行修改，从而提升了部署和更新的效率。

- **环境变量注入**  
   环境变量注入是容器定制中一种非常有效的方式，可以在容器启动时传递动态参数。这种方式适用于配置经常变动、需在容器启动时确定的场景。

### 高级定制技巧

- **多阶段构建**  
   使用 Docker 的多阶段构建能够大幅减少镜像的体积，并提高构建效率。在多阶段构建中，不同阶段分别用于构建、测试、打包等任务，最终只有需要的文件会被保留下来，从而降低最终镜像的体积。

- **最小镜像体积优化**  
   通过精简镜像中的不必要部分，可以有效降低镜像体积。使用更精简的基础镜像（例如 `alpine`），并去除不必要的文件和工具，可以使得镜像更加轻量，提高部署效率和安全性。

- **安全加固**  
   对容器镜像进行安全加固是保证其安全性的关键。可以通过使用非 root 用户运行容器、限制容器的网络权限、使用只读文件系统等手段，增强镜像的安全性，减少潜在的攻击面。

- **性能调优**  
   为了优化容器运行时的性能，可以根据实际需求对镜像进行优化。包括调整容器的资源限制、优化软件包的安装方式、通过缓存机制提高构建速度等。合理的性能调优可以确保容器在高负载环境下仍能保持稳定和高效运行。
